# Classroom future-auction disclosure audit

Reviewed `server/rooms.ts`, `simulation/types.ts`, and procurement interfaces. This is a verified exposure inventory, not a claim of completed privacy redaction.

The current room view clones and returns the complete `Game`. It masks actual future weather and auction seed, and removes other roles' current bids and bid-composition snapshots. It does not hide future auction lots' quantities or estimates. `region.stands` includes future `auctionWeek`, `volume`, `mix`, `askingPrice`, productivity and harvest cost. `game.stands[].remaining` independently exposes initial future quantities. Each history `snapshot.stands` can repeat those values. A linked season's `baseRegion.stands` is another copy. Stand geometry and hectares can also inform an estimate even if exact volumes are hidden. A hidden UI row would not protect this payload.

Safe implementation needs an explicit scenario disclosure policy and a separate classroom observation schema: publish only lots whose release week has arrived, with `unreleased` placeholders for IDs/geometry when geography should remain visible. Represent unavailable quantities as unavailable, never zero. Apply the same policy to current definitions, state, history snapshots and linked-season definitions. Keep server-side simulation definitions unchanged. Update map/table/target calculations to exclude unknown quantities and label partial totals; preserve instructor-only full access when the exercise requires it. Test serialized responses by inserting sentinel quantities in every nested source before and after release, for all student roles, plus malformed and recovered sessions.

Bundled teaching scenarios already contain public lot data. Genuine hidden future quantities additionally require server-only randomized/author-authored realizations rather than reusing values shipped in the client bundle. Local standalone simulations cannot promise secrecy from their own user. No broad redaction was applied during this audit because returning partial objects under the existing full-Game contract would silently corrupt planning estimates or fail validation.

## Implementation boundary confirmed in the follow-up review

`Classroom.View.game` is explicitly typed as `Game` and is passed into OperationsMap, CrewTimeline, ReservationDesk and processing/transfer desks. OperationsMap currently renders `remaining` and roadside stock unconditionally in stand tooltips. Save validation requires positive definition volume/asking price and the identity `remaining + harvested = definition.volume`. Therefore missing or zero-valued placeholders cannot safely masquerade as simulation state. Adding a marker only to the tooltip would leave other consumers able to derive misleading totals. No incomplete policy flag or randomization was added.

The complete implementation should be sequenced as follows:

1. Define a validated instructor creation policy with volume/price multiplier ranges and release-week visibility. Default existing rooms to the current public teaching scenario. Generate each room's auction realizations with server randomness; rebuild matching initial StandState before any plans or history exist. Retain private realizations only in the persisted room. Reject enabling the policy after campaign creation.
2. Introduce a discriminated ClassroomObservation: released lots carry known quantities; unreleased lots carry identity/location/release date and `unreleased: true`, with no volume, mix, asking price, stock or remaining fields. This must not be cast to Game or accepted as a saved campaign.
3. Give map display and classroom planning desks explicit observation adapters. Production and transport controls enumerate only owned/released stands; charts mark totals as partial; unreleased map placeholders say “Not released.” Keep drafts server-authored and plan validation server-side. Disable any client simulation/advisor that requires unreleased input; do not fill unknown values with zero to run it.
4. Build the serialized response from an allowlist, including historical observations filtered according to the chosen release rule. Exclude full linked-season base regions and raw history snapshots from student responses. Instructor views can retain privileged definitions by an explicit role branch. Keep cohort summaries unchanged because they contain no lot quantities.
5. Test every student role with unique sentinel secrets in current definitions/state, history snapshots and linked-season state; assert no secret reaches serialized responses before release. Test due-week release, unrelated unreleased lots, restart consistency, malformed policies, instructor access, and exact cash/harvest results after release. Exercise map tooltip and all affected planning panels against unreleased observations before enabling the feature.

This is a cross-component API migration rather than a local redaction patch. The existing public-scenario behavior remains accurate and unchanged pending that migration; the application does not claim hidden future auction quantities.

## Implemented resolution: subset observations

The later implementation uses a valid subset of Game rather than numeric placeholders. An optional `auctionDisclosure` creation policy declares `release-week` visibility and independent volume/price multiplier ranges. The classroom server realizes each auction before constructing its state, retains that authoritative state privately, and persists it normally. Existing scenarios remain unchanged by default. The Classroom creation checkbox uses 0.8–1.2 ranges unless an imported policy supplies explicit ranges.

Student responses remove all not-yet-released auction definitions and matching StandState rows, history snapshot rows, plan/schedule/reservation references. Optional linked-season/stewardship embedded models are omitted while lots remain hidden. A separate `withheldAuctions` list supplies only ID/release week; the interface explicitly marks map/totals as released-only. Instructor observations retain full access. The server rejects participant mutations naming unreleased lots. The policy requires at least one guaranteed/private lot, preventing an empty visible scenario.

Verification: focused auction/rooms/weather suites pass nine tests. The auction suite validates serialized subset Game with `parseGame` before and after week advancement, checks absent future definitions/state, range-constrained realization, restart consistency, release-time exposure, illegal early bids and malformed policy rejection. Browser verification is tracked separately by the parent task. This changes only networked classroom privacy: public standalone scenarios still provide their complete local teaching data.
